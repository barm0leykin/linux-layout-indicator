## M0-01. Детект смены раскладки

**Работает.** Подписка:

```c
XkbSelectEventDetails(dpy, XkbUseCoreKbd, XkbStateNotify,
                      XkbGroupStateMask, XkbGroupStateMask);
```

Событие приходит с `event.type == eventBase + XkbEventCode`, `xkb_type == XkbStateNotify`,
поле `state.group` — индекс раскладки. `eventBase = 85`, opcode = 135.

**Живые нажатия `Alt+Shift`:** 4 переключения → 4 события, ровно по одному на каждое.
Поле `changed = 0x1190` (GroupState | GroupLock | CompatState | CompatLookupMods).

```
+23666 ms  group=1     (0→1)
+26126 ms  group=0     (1→0)
+26678 ms  group=1     (0→1)
+36204 ms  group=0     (1→0)
```

**Важно:** синтетическое переключение через `xdotool key alt+shift` даёт **8 событий**
(4 пары 0↔1) и возвращает группу в исходное состояние — артефакт XTEST, не свойство XKB.
**Нельзя использовать `xdotool` как эталон в автотестах.** Для тестов — реальный ввод
или `XkbLockGroup` (даёт ровно одно событие).

**Влияние на продукт:** дедупликация в presenter'е нужна как защита от дребезга, но не
является обязательным механизмом. Сравнивать новую группу с последней отображённой.

## M0-02. Группа → код раскладки

Три источника дают разное:

| Источник | Что даёт | Пригодность |
|---|---|---|
| `XkbGetNames(XkbGroupNamesMask)` | `English (US)`, `Russian` — **человекочитаемые имена**, не коды | только для подписи/фолбэка |
| `setxkbmap -query` | `layout: us,ru` — коды в порядке групп | основной источник |
| `~/.config/kxkbrc` | `LayoutList=us,ru`, `Options=...` | равнозначен setxkbmap, читается без X |

**Решение:** коды `us,ru` → `EN,RU` брать из `kxkbrc` (файл, не требует X-запроса)
с фолбэком на `setxkbmap -query`. `XkbGetNames` использовать только как запасной
источник отображаемого имени.

**Побочная находка:** в `kxkbrc` стоит **`SwitchMode=WinClass`** — KDE переключает раскладку
**по приложению**. Это означает:

1. Событие смены группы может приходить **не от `Alt+Shift`, а от смены фокуса окна** — KDE
   сам восстанавливает раскладку приложения. Такие события тоже надо показывать (пользователь
   не видит, какую раскладку ему подставили).
2. Фича «показать раскладку при фокусе на поле» (FR-4) становится **полезнее**: она объясняет
   пользователю, что произошло при переходе между окнами.
3. В PRD/задачах это надо отразить явно (см. «Влияние»).

## M0-03. Оверлей — ПОДТВЕРЖДЕНО

Проверено на живом X-сервере (`spike/overlay.c`):

| Критерий | Как проверено | Результат |
|---|---|---|

| WM не управляет окном | `xwininfo`: `Override Redirect State: yes` | ✅ |
| Окно видимо | `xwininfo`: `Map State: IsViewable` | ✅ |
| Рисуется **поверх** окон | снимок композитного экрана в области бейджа содержит пиксели бейджа, а не окна под ним | ✅ |
| Текст отрисован | гистограмма: 3828 px фона `#171819` + 44 белых px текста (88×44 = 3872) | ✅ |
| Не попадает в список окон WM | `_NET_CLIENT_LIST` не содержит id окна | ✅ |
| **Клик проходит сквозь** | `xdotool mousemove` в центр бейджа → окно под курсором = id приложения, не оверлея | ✅ |
| Композитор присутствует | `_NET_WM_CM_S0` имеет владельца | ✅ |

Механизм пустой input-shape: `XShapeCombineRectangles(dpy, win, ShapeInput, 0, 0, NULL, 0, ShapeSet, Unsorted)`.

**Не проверено:** перехват фокуса — по построению `XSetInputFocus` не вызывается, а override-redirect
окно WM не фокусирует; отдельный тест не проводился.

**Ограничение прототипа:** фон залит на весь прямоугольник 88×44 — скругления и прозрачных полей
нет (в проде нужны). Текст рисуется ядровым шрифтом `fixed` без сглаживания и шейпинга —
в Rust будет `ab_glyph`/`cosmic-text`.

## M0-05. Каретка через AT-SPI — ПОДТВЕРЖДЕНО (с оговорками)

**Исходное состояние:** accessibility в сессии выключена.

```
org.a11y.Status IsEnabled           = false
org.a11y.Status ScreenReaderEnabled = false
```

При выключенной a11y приложения отдают только верхний уровень дерева
(`frame children=1` → `getChildAtIndex(0) == None`).

**Эксперимент:** включили `IsEnabled=true` (только его, без `ScreenReaderEnabled`),
затем проверили два класса приложений.

### Что получилось

| Сценарий | Результат |
|---|---|
| Уже запущенные VS Code / Chrome | ❌ дерево осталось обрезанным — флаг читается при старте приложения |
| **Свежезапущенное GTK3-окно с полем ввода** | ✅ **каретка получена** |

Замер на GTK-окне (`spike/gtk_entry_test.py` + `spike/caret_probe.py`):

```
[gtk_entry_test.py] role=text -> caret=16  rect=(5688, 707, 0x25)  за 2 мс
```

`caret=16` совпадает с длиной строки «проверка каретки» — позиция верная.
Время получения: **2 мс**.

### Выводы для реализации

1. **Механизм работает и дёшев** (единицы миллисекунд), но требует **включённой
   accessibility во всей сессии**.
2. **Приложения должны быть запущены после включения a11y.** Уже работающие
   VS Code/Chrome сами не перестраиваются — нужен перезапуск приложения
   (или `--force-renderer-accessibility` для Electron/Chromium).
3. `getCharacterExtents` в конце строки вернул **ширину 0** (`0x25` = width 0, height 25).
   Это нормально — для позиционирования берём `x` как точку каретки, `height` — как
   высоту строки. Обработку `width == 0` заложить явно.
4. **T2 не может быть режимом по умолчанию:** он требует осознанного действия
   пользователя (включить a11y) и перезапуска приложений. Дефолт остаётся T0 (курсор мыши).
5. **Ценность T2 для основных сценариев снижается:** VS Code и Chrome — главные
   целевые приложения, и им нужен перезапуск. В README это надо написать прямо.

### Стоимость

- Проба одного окна: ~2 мс (обход дерева с бюджетом узлов).
- Стоимость того, что все приложения начинают строить полные a11y-деревья
  (память/CPU), **численно не измерена** — требует отдельного замера (M0-06).

### Откат

После теста `IsEnabled` возвращён в `false`, `ScreenReaderEnabled` не менялся.
Система в исходном состоянии.

### Дополнительно: активное окно

`STATE_ACTIVE` в a11y стоял **одновременно на нескольких окнах** разных приложений
(kando + Chrome + VS Code). Определять активное окно через a11y нельзя.

**Решение:** активное окно — только из X11 `_NET_ACTIVE_WINDOW`; a11y использовать
исключительно для поиска каретки **внутри** уже известного окна.

## M0-07. EWMH и геометрия

Поддерживаются: `_NET_ACTIVE_WINDOW`, `_NET_CLIENT_LIST`, `_NET_CLIENT_LIST_STACKING`,
`_NET_WORKAREA`, `_NET_WM_STATE_FULLSCREEN`, `_NET_WM_FULLSCREEN_MONITORS`,
`_NET_FRAME_EXTENTS`, `_GTK_FRAME_EXTENTS`.

- `_NET_ACTIVE_WINDOW` корректно возвращает окно (проверено: VS Code, `WM_CLASS` совпадает).
- `_NET_WM_STATE_FULLSCREEN` поддерживается → подавление в fullscreen реализуемо.
- `_NET_WORKAREA = 0,0,7040,1388` — **один прямоугольник на весь десктоп**, при трёх мониторах
  разных разрешений. Значит:

  **Ограничение по краям считать по геометрии конкретного монитора (XRandR), а не по workarea.**
  Workarea годится только для отступа от панели.

- DPI 96 → масштаб 1x. HiDPI пока не воспроизводится, но код должен быть в логических пикселях.

## M0-09. Wayland: замер на KDE Plasma (2026-11-24)

Стенд: u24, Ubuntu 24.04.5, **Plasma 5.27 Wayland** (`kwin_wayland`), Qt 5.15.13,
GTK 3.24.41. Проверялось на собранном приложении, без правок под Wayland.

| Сценарий | Результат | Детали |
|---|---|---|
| Источник раскладки | ✅ | `org.kde.KeyboardLayouts`: `старт 0 (US) → 1 (RU) → 0 (US)` по сигналу `layoutChanged` |
| Бейдж (оверлей) | ✅ через Xwayland | окно `0xe00001`, фон `#1B1C1D`, рамка `#434548`, текст белый |
| Трей (SNI) | ✅ | элемент `org.kde.StatusNotifierItem-<pid>-1` зарегистрирован |
| Каретка GTK (gedit) | ✅ | `фокус поля: каретка (71, 96)` |
| Каретка Qt (Kate) | ❌ | то же ограничение Qt, что и на X11 |
| Триггер по смене окна | ⚠️ ненадёжен | при фокусе нативного Wayland-окна `_NET_ACTIVE_WINDOW` становится `0x0` |
| Подавление fullscreen | ⚠️ не проверено | `_NET_WM_STATE` отражает только X11-окна; KWin-скрипт для теста не запустился |
| Движок клика (XInput2) | ❌ по устройству | raw-события Xwayland не отражают ввод в нативные Wayland-окна |

**Выводы:**

1. **KDE Wayland пригоден уже сейчас**: раскладка (D-Bus) + оверлей (Xwayland) +
   трей работают. KWin-эффект не нужен.
2. **Каретка под Wayland работает для GTK** и не зависит от композитора (AT-SPI — D-Bus).
3. **Деградации под Wayland:** триггер по смене окна (`_NET_ACTIVE_WINDOW` → 0),
   движок клика (Xwayland не видит нативные окна), подавление fullscreen (не проверено).
4. Отсюда для Wayland предпочтителен режим `auto` с опорой на каретку из AT-SPI,
   а не на клик/активное окно.
